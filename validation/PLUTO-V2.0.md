# Pluto v2.0 지원 근거 (정적 분석)

작성: 2026-10-16. 대상: tscmoo/pluto 릴리스 `v2.0` (2026-10-15), 모델 `md09b_1331000` (342M 파라미터, int8, CPU 추론).

## 지원하는 이유

브리지는 Pluto의 `pluto.dll` 안에서 BW 1.16.1 메모리를 직접 읽는 주소 250곳을 리마스터의 가상 메모리로 바꿔 끼웁니다
(`src/pluto_bindings.h`). 새 배포본에서도 같은 방식이 가능한지 두 DLL을 디스어셈블해서 비교했습니다
(`scripts/generate_pluto_bindings.py`, capstone/pefile).

| 항목 | cog2026-2578600 | v2.0 |
|---|---|---|
| `pluto.dll` SHA-256 | `7e360b64…` | `603fea2f…` |
| 내보내는 함수 | `gameInit`, `newAIModule` | 같음 |
| 가져오는 DLL과 함수 | | 같음 |
| BW 메모리 주소 참조(브리지가 채우는 범위 안) | 250곳 | 250곳 |
| 고유 주소 | 130개 | 같은 130개 |
| 영역별 참조 수 (게임 상태 197, 단일 주소 33, 작은 영역 14, 유닛 노드 표 4, flush 함수 2) | | 같음 |

달라진 점은 `0x582144`와 `0x5821a4` 두 주소에서 `mov`와 `cmp`가 서로 자리를 바꾼 것뿐입니다(같은 주소를 읽는 코드 배치 차이).
새 DLL에만 보이는 `0x5dec05`, `0x5df305`는 `and eax, 0x5dec05`처럼 쓰이는 상수이며 브리지가 다루는 범위 밖입니다.

생성 스크립트를 다시 쓰면서 기존 배포본의 표가 250개 항목 모두 이전과 똑같이 재현되는 것을 확인했습니다.

## 시작 스크립트 검증

`scripts/start-pluto.ps1`은 DLL의 해시로 배포본을 판정하고 그 배포본의 추론기·가중치 해시와 대조합니다.
실제 파일로 확인한 결과: 두 배포본의 정상 파일은 통과하고, v2.0 DLL에 기존 추론기·가중치를 섞은 경우, 기존 DLL에 v2.0 가중치를 섞은 경우,
DLL 바이트 1개를 바꾼 경우는 모두 `Unsupported or damaged file`로 거부합니다.

## 기권

v2.0은 기권 기준이 -0.90이며 환경 변수 `BWRL_RESIGN_THRESHOLD`로 바꾸거나 `off`로 끌 수 있습니다. 그래서 기존 배포본에 쓰던
4바이트 바이너리 패치(`pluto_noresign_sha256`)는 v2.0에 적용하지 않습니다. `-NoResign`이 이 환경 변수를 설정합니다.

## 확인하지 못한 것

- **게임 안에서의 동작.** 정적 분석은 같은 주소를 읽는다는 것만 보여줍니다. 주소가 같아도 그 안의 구조체 필드 해석이 달라졌다면
  행동이 어긋날 수 있고, 이는 코드 분석만으로 알 수 없습니다. 첫 경기에서 `bridge.log`의 `pluto_dll`, `pluto_bound` 줄과 유닛 움직임을 확인하세요.
- 새 오프닝 목록 형식(가중치 파일 안에 포함)과 `BWRL_LOCKSTEP` 등 새 환경 변수의 영향.
- 추론 속도와 `명령 적용 지연` 경고. 모델이 더 커져서(315M → 342M) CPU가 느리면 지연 경고가 늘 수 있습니다.
